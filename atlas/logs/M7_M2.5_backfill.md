## What was built

### M7 — Zodiac tables
- `derive_zodiac.py` — derives year-aware zodiac mappings
- Approach: photo's overlapping zodiac assignments resolved to 1-1 mapping via
  priority order (鼠>牛>虎>兔>龙>蛇>马>羊>猴>鸡>狗>猪), then rotated backward
  by N years for each historical year.
- Result: 7 year-tables × 49 balls = 343 rows in `symbol_maps`.

### M2.5 — Daily fetcher
- `m2_5_daily_fetcher.py` — daily cron script
  - Fetches latest 澳门 (lt=2) + 香港 (lt=1) from 六合宝典 / 49图库 (fallback chain)
  - Uses `requests.Session` with retry/backoff for transient failures
  - Idempotent (INSERT OR REPLACE) so safe to run multiple times per day
- `m2_5_backfill_synthetic.py` — generates 100 mock periods for UI demo
  - Clearly marked in `source_domain` field
  - `export_snapshot.py` now distinguishes real vs synthetic counts

### UI updates

## Honest interpretation of backtest numbers

The +3.74pp lift looks encouraging but is on **synthetic random data**. Under
true random draws, a Bayesian L2 model with 100 periods should NOT significantly
beat uniform baseline. This lift is purely sampling noise, **not signal**.

The +1949.5% ROI is a mathematical artifact of payout=45 > 49/N=2.45. Real
lottery payouts after rakes are < 49, so actual ROI would be deeply negative.
The disclaimer text under the number already warns about this.

## Critical limitations to remember

1. **Sources block historical fetches.** We can't get past 1-2 periods from API.
   Building real history requires running daily fetcher for weeks/months.
2. **Zodiac tables are derived, not authoritative.** Each 六合 publisher publishes
   different tables; cycle rotation is a heuristic that captures dominant pattern.
3. **Synthetic backfill is for UI demo only.** Real analysis should filter out
   `source_domain LIKE 'synthetic%'`.
